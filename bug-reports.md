# NURAE — Bug Reports & Fixes

A running log of every bug reported during live testing, with the diagnosed
root cause, the shipped fix, and current status. Newest entries are added at
the bottom. The technical work log lives in [`worklog.md`](./worklog.md);
this file is the user-facing history of what broke and how it was resolved.

| ID | Reported symptom | Root cause | Fix | Status |
|----|------------------|------------|-----|--------|
| BR-001 | Registering a new account says "failed to verify"; verification mail never arrives | `setup.sh` reused a stale build/running server after `git pull` (no `/api/auth/verify` in the old process), and when Gmail SMTP failed the register UI still claimed the code was sent | Stale-build detection + stale-server replacement in `setup.sh`; register now returns an actionable mail error (`mailFailureHint`), verify step shows "email could not be sent" + Resend button; app-password whitespace stripped | FIXED — V00.01.010 |
| BR-002 | Official NURAE CS bot: cannot configure API keys or system prompt | Bots created before the provider rework carried `provider='zai'` (removed), so the key field didn't render; config dialog was buried | Legacy zai rows auto-migrate to openrouter at boot; "Configure keys & prompt" button directly on the Official Bot card (API key, Telegram token, prompt, model); "Reset prompt to official" + official CS prompt shipped | FIXED — V00.01.010 |
| BR-003 | Telegram shows AI output with raw markdown — `#`, `*` appear literally | Replies were sent with no `parse_mode`, and Telegram renders plain text as-is | New dependency-free markdown → Telegram-HTML converter (headings→bold, `**`/`_`→bold/italic, code→`<code>`/`<pre>`, links, lists, quotes, tables), replies sent with `parse_mode=HTML`; long replies chunked ≤4096; if Telegram rejects the HTML the raw text is resent plain so the reply always arrives | FIXED — V00.01.011 |
| BR-004 | OTP mail never reaches any inbox; log shows `connect ENETUNREACH 2404:6800:…:465` | The device's network has no IPv6 route, but DNS answered `smtp.gmail.com` with an AAAA record first and nodemailer dialed it — connection unreachable. The app password itself was valid all along | IPv4-first DNS order forced in the mailer module (`dns.setDefaultResultOrder('ipv4first')`); ENETUNREACH-specific setup hint added; live SMTP delivery test passed (Gmail `250 OK`) with the owner's credentials | FIXED — V00.01.011 |
| BR-005 | Dev log spams `A Node.js module is loaded ('node:dns') which is not supported in the Edge Runtime` on every request | `src/instrumentation.ts` is compiled for BOTH the Node and Edge runtime targets in dev; the IPv4 DNS fix placed there tripped Turbopack's static analysis on every compile | Node-only DNS side effect moved back into `src/lib/nurae/auth/mailer.ts` (Node-only bundle, runs before any SMTP call); `instrumentation.ts` now contains no Node-only imports | FIXED — V00.01.012 |
| BR-006 | Dev log warns `The "middleware" file convention is deprecated. | BR-016 | "When someone starts the bot…" cannot be built — `/start` always answers the built-in text | The pipeline intercepted `/start` before any reply rule, so a custom welcome behavior/rule could never fire | `/start` now checks for a behavior/rule bound to it first (compiled start behaviors land there); the built-in text remains the fallback when none exists; deep-link payloads are still logged | FIXED — V00.02.001 |
| BR-017 | A bot started from the **production** site does not work, while the same bot works in dev (`npm run dev`) — `npm run build && npm run start` kills it | Two structural defects, both silent: (1) the standalone production server does `process.chdir(__dirname)` → its working directory is `.next/standalone`, so a relative `DATABASE_URL=file:./db/custom.db` (the default) opened a **build-time snapshot copy** of the database traced into the build output; (2) the auto-generated secret-key file and the uploads folder resolved by cwd too — production got a **different master key**, so Telegram tokens / AI keys / webhook secrets encrypted in dev could not be decrypted. Result: the site looks fine but runs on a frozen DB that resets on every rebuild, and bot secrets fail silently | All data paths (DB, key file, uploads) now resolve against the **project root** (`src/lib/paths.ts`, standalone-aware); `npm run start` boots through `scripts/start-prod.mjs` which loads the project `.env`, pins `NURAE_APP_ROOT` and makes `DATABASE_URL` absolute before launch; the build script strips `db/`, `.env` and uploads out of `.next/standalone` (no more snapshot, no more secrets inside deployable artifacts). Verified end-to-end in production mode: register → create behavior bot → publish → Telegram webhook `/start`, `/prices`, free text → all replied correctly against the real database; also verified a bare `node .next/standalone/server.js` stays on the right DB | FIXED — V00.02.002 |
| BR-018 | The agent workflow and the chat workflow behave differently (user report: "not consistent") — files attached in chat never reached the agent, the handoff task appeared twice, every build request forked a NEW agent session (and risked a duplicate draft bot), the agent composer could not attach files, agent sessions had no rename/archive/delete, and the agent empty state could not accept input | The agent view was a separate implementation, not a mirror of the chat: `files_list` filtered by session id (chat-attached files invisible), the handoff wrote BOTH a system TASK entry and a user entry (duplicate display; the file note lived only in the filtered-out system entry), handoff always called `ensureAgentSession` (no continuation), the agent route/UI lacked attachments and session management, approval-only turns persisted empty user bubbles | One shared workflow: `files_list` unions the session's chat-attached files (state `fileRefs`) and the prompt names them with ids; handoff CONTINUES the user's latest active agent session (7-day window) instead of forking; the duplicate system task entry is gone (the task is the session's first user message); the agent route/UI accept `attachmentIds` (ownership-checked like chat, merged into fileRefs); the agent sidebar uses the shared `SessionList` (rename/archive/delete, same as chat); approval-only turns no longer write empty user entries; agent turns share the chat rate-limit budget; optimistic sends roll back honestly on error in BOTH views; the new-build sidebar entry appears even when the first turn fails | FIXED — V00.02.002 |

## Notes

- Every fix above ships with regression coverage in `tests/nurae/` — the
  suite count is 202/202 as of V00.02.002-beta-03 (page-level UI changes are
  additionally verified in a real browser; React components have no vitest
  harness yet).
- BR-004 evidence: with the owner-provided Gmail app password, a real
  verification-template email was delivered from the sandbox (`250 2.0.0 OK`).
  If mail still doesn't arrive on the device after updating: check spam, use
  the **newest** code (old ones are invalidated), and confirm the two
  `NURAE_GMAIL_*` variables in `.env` — see SETUP.md §10 Troubleshooting.
- Credentials shared in chat should be rotated once testing is done
  (Google Account → Security → App passwords), and the OpenRouter key that
  was exposed earlier should be rotated as well.
